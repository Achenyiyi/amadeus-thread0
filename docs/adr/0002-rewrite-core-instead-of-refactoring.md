# 重写核心，不在旧代码上原地重构

第一版的核心放进新包 `amadeus/`，按第一版的设计从头写，不在 `amadeus_thread0/` 上一步步删减。原地重构的好处是每一步都有一个能跑的旧系统，可重构开始时旧系统已经跑不起来了（开发机上没有一个装齐依赖的环境），终点又几乎不留旧代码：和第一版对应的旧代码现在有 43,041 行，第一版最多 6,000 行，而且没有哪一块能整块留下。原地走的话，力气会花在给注定要删的代码解耦、改 1,841 个绑在旧结构上的测试上。重写的风险是停在半路，所以先搭一条最薄的对话线，之后每一步加一项能力。

做法：

- 新包叫 `amadeus`，放在仓库根目录，用 `python -m amadeus` 启动。不沿用 `amadeus_thread0`，因为 `thread0` 是旧的默认 thread_id，而多条 thread 已经砍掉了。仓库名不变。
- 开工第一步就删掉旧代码，直接在 main 上做，不开长分支。旧包、旧测试、旧 eval 脚本和按旧结构写的配置一起删，本地的旧运行数据和存档核对后清掉。要查旧代码，用 tag `pre-refactor`。
- 只搬知识，不搬文件。新核心不 import 旧包，也不整文件复制；照着旧代码重写的小段按新接口写，并配上新测试。
- 骨架是最薄的一条对话线：你的一句话 → 拼提示词（人格设定、当前本地时间、最近的对话）→ 生成 → 清洗 → 打印 → 存进历史，每条都带发送时间。回复后评估、心情、关系和长期记忆，之后每一步加一项。
- 从骨架起，每一步结束时全量测试都用假模型跑通，CLI 能用真模型和她聊一轮。旧版本不再维护。
- 过渡期的数据不迁移，存储格式一变就换一个数据目录。第一版完成以后再改格式，才写迁移。

## 否决的做法

- **原地重构**：理由见上。
- **新旧并存到第一版达到验收线再删，或者把旧代码挪进 `legacy/`**：旧版本不再维护，留在树里只会干扰搜索和 agent，删除也容易一拖再拖。
- **整文件搬运旧代码**：旧接口和旧概念会跟着回来。

## 被推翻的旧约定

- `CLAUDE.md` 的 "New graph logic goes in `graph_parts/`, not `graph.py`" 和 "Runtime/execution logic goes in `runtime/`"：旧包整个删掉，新包的结构由 spec 定。
- `CLAUDE.md` 要求改动前先查 `AGENTS.md` 的 unlock contract 和 preserved baseline；`AGENTS.md` 的「Backend Freeze Gate Baseline」一节要求之后的改动 "preserve this baseline rather than reopen core-loop redesign"。重写本身就是重新设计核心回路，这些 baseline 的 audit 脚本在第一步随 `evals/` 一起删除。
